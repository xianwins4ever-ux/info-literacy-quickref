## 三、本轮最有价值的 6 个发现

### 3.1 知网分面必须"点开"才加载

11 个分组里**只有前 3 个默认有条目**，其余 8 个（作者/机构/年度/文献来源/基金…）`dd li` 数量为 0，
**必须点击 dt 标题**才 AJAX 拉取。脚本已自动展开。

→ 这让「发文量最多的作者」「论文最多的单位」这类题有了自动化路径。
实测题14 → 刘奇超(21) 第一；题11 → 北京邮电大学(138) 第一。

### 3.2 知网两个致命坑

**引号必须英文半角**：半角 `"AI"` → 2365；全角 `“AI”` → 1870（差一千多条）。

**「或」必须写在括号里**：行间只有 AND/OR 下拉、没有括号，混用会按 AND 优先错误结合。
```
篇名 AI OR 篇名 人工智能 AND 主题 法律 OR 主题 法规
→ 实际 = AI OR (人工智能 AND 法律) OR 法规   ← 错！
```

### 3.3 万方滑块：等 + 预热

原实现两个缺陷导致连续 3 轮全败：
1. **没等滑块出现**（阿里云验证码异步注入，约 3 秒后才出现）
2. **缺少"预热"**（直接 mousedown 匀速拖被判机器）

修法：轮询 20s 等元素 + hover 400ms → mousedown → 300ms → 抖动 5 步 → 主拖 55 步 → 微调 → mouseup。
**实测第 1 次即通过。**

### 3.4 国图古籍 searchType=1002 才是正确入口

同一个词「南岑吳氏宗譜」：
- `searchType=10024` → 2123 条，**前 12 条全是别的宗谱**（相关性极差）
- `searchType=1002` → 9255 条，**第 1 条就是目标** ✅

古籍详情页结构也完全不同：不是 `<label>`，而是「字段：值」纯文本行 + 「第N册 在线阅读」列表。
**「共有几册」= 数「第N册」个数。**

### 3.5 NCBI Bookshelf 网页有 reCAPTCHA，改用 `db=books`

`ncbi.nlm.nih.gov/books/?term=` 现在返回 reCAPTCHA，**浏览器也过不去**。
正确做法：用 E-utilities 的 `db=books`（纯 API）：
```
esearch.fcgi?db=books&term=<书名>   → count + idlist
esummary.fcgi?db=books&id=<ids>     → bookinfo XML 含 <PublicationStatement>
```
`"Oxford (UK): Oxford University Press; 2016 Dec."` → 冒号后分号前就是出版社。

### 3.6 反直觉：搜索页是空壳

- **辟谣平台**：`frontsql.htm?kw=` 是空壳，真实接口是 `so.news.cn/xhtvapp/rumourSearch`
- **12371**：站内不存在"全国优秀共产党员展播"这个栏目名，实际是 `/special/dzby/dy/`
- **庭审公开网**：高级检索（案号精确字段）必须登录，但普通检索 `/search/common?keywords=` 可直连
- **UNESDOC**：headless 是硬墙（环境指纹判定），必须 headed

**教训：照题面的栏目名去搜，常常一无所获。**

## 六、四条铁律（沿用）

1. **API 优先** —— 先问"这系统有没有接口"，别问"页面怎么点"
2. **元数据优先** —— 页数/年份/作者这类答案就在元数据里，**不下载文件**
3. **一次调用拿全** —— "搜索→详情→提取"串在一个脚本里
4. **看到答案就交** —— 不做"双重验证"（除非两个来源矛盾）

**另加一条**：**脚本报"无记录"时先怀疑拦截**。任何"查无此 X"的结论，都要先确认脚本没有报请求失败。
